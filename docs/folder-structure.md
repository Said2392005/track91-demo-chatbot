# Folder Structure

What every folder and file in this repo is for. Generated by reading the actual source tree and
module docstrings, not from memory — if a file's purpose changes, this doc can drift, so treat it
as a map, not a contract.

```
untitled folder 3/
├── docs/            # Design docs, ADRs, per-phase writeups (see docs/fleet-chatbot-roadmap.md)
└── backend/         # The FastAPI application — everything runnable lives here
```

## `backend/app/` — application code, by module

The app is organized by **pipeline stage**, not by REST resource: a chat message flows through
`api` → `services` → `agent` (the LangGraph graph), and the graph's nodes call out to `nlu`,
`router`, `tools`, `rag`, `kb`, `db`, `llm`, and `memory` along the way. `core` holds cross-cutting
config/logging/security used everywhere.

### `app/main.py`
The FastAPI app factory. Builds every process-lifetime singleton (Mongo connection, the compiled
agent graph, LLM provider, GPS client, KB collection) once at startup via `lifespan`, storing them
on `app.state`. Also registers CORS, the correlation-ID/structured-logging middleware, and the
global exception handler.

### `app/core/` — cross-cutting concerns
| File | Purpose |
|---|---|
| `config.py` | `pydantic-settings`-based config, reads `.env` — Mongo URI, LLM provider selection + API keys, JWT secret, log level, ChromaDB paths |
| `logging.py` | Structured JSON logging with `request_id`/`session_id` correlation via `contextvars` |
| `security.py` | Password hashing (bcrypt, offloaded to a thread) and JWT issuing/verification |
| `taxonomy.py` | The 33-intent taxonomy as code, transcribed from `docs/phase-1-planning/intent-taxonomy.md` — single source of truth every other module imports from |

### `app/api/` — HTTP layer (thin)
| File | Purpose |
|---|---|
| `deps.py` | Dependency-injection providers (`get_db`, `get_graph`, `get_current_user`, etc.) — the two roots (`get_db`/`get_graph`) read off `app.state`, which is what makes them overridable in tests via `app.dependency_overrides` |
| `object_id_param.py` | Parses/validates a MongoDB ObjectId from a path/body string param, 400s if invalid |
| `routers/auth.py` | `POST /auth/login` |
| `routers/chat.py` | `POST /chat`, `GET /chat/{session_id}/history` |
| `routers/health.py` | `GET /health` |

Routers only parse input, call a service, and shape the response — no business logic lives here.

### `app/schemas/` — Pydantic request/response models
`auth.py` (`LoginRequest`/`LoginResponse`), `chat.py` (`ChatRequest`/`ChatResponse`/
`ChatHistoryResponse`/`ChatMessageOut`).

### `app/services/` — orchestration layer between routers and the graph
| File | Purpose |
|---|---|
| `auth_service.py` | Login: verify credentials, issue a JWT |
| `chat_service.py` | Chat orchestration: ensure a session exists, invoke the agent graph, persist the transcript, shape the result for the router |

### `app/agent/` — the LangGraph graph (Phase 10)
| File | Purpose |
|---|---|
| `graph.py` | Assembles the compiled `StateGraph` from all the node functions — pure wiring, no business logic of its own |
| `state.py` | The graph's state schema — all IDs kept as strings, never raw `ObjectId` |
| `nodes.py` | Every graph node: `entry_node` (loads active entities), `semantic_analysis_node` (NLU), `router_node`, `clarify_node`, `gps_tool_node`/`mongo_tool_node`/`rag_tool_node` (subsystem dispatch), `synthesis_node` (LLM phrasing), `memory_update_node` |
| `serialization.py` | Converts between `ObjectId` and string at the state boundary — required because LangGraph's `MongoDBSaver` checkpointer can't msgpack-serialize a raw `ObjectId` |
| `response_synthesis.py` | Turns raw LIVE_API/MONGO_REPO tool results into natural-language text via the LLM |
| `templates.py` | Fixed (non-LLM) response strings for meta intents (greeting/goodbye/chitchat/out-of-scope), backlog-unsupported, unknown-intent, and the "LLM unavailable" degraded message |

### `app/nlu/` — natural language understanding (Phase 6)
| File | Purpose |
|---|---|
| `intent_classifier.py` | Two swappable strategies behind one interface: rule-based (default, deterministic) and LLM-based (config-driven alternative) |
| `trigger_patterns.py` | The phrase/regex/co-occurrence tables the rule-based classifier scores against — one entry per intent |
| `entity_extractor.py` | Orchestrates normalization, repository lookups, and dictionary matching to pull entities (vehicle, driver, date range, etc.) out of an utterance |
| `normalization.py` | Vehicle registration number normalization (e.g. casing/spacing) |
| `dictionaries.py` | Synonym dictionaries for enum-valued entities |
| `date_parser.py` | Parses relative/absolute date expressions into a `date_range` |
| `coreference.py` | Resolves pronouns ("it", "its", "that one") against session memory |
| `pipeline.py` | Combines classification + extraction + the CLARIFICATION_NEEDED decision into one `analyze()` call |

### `app/router/` — deterministic intent → tool routing (Phase 9, ADR 003)
| File | Purpose |
|---|---|
| `router.py` | The router itself: given an intent + entities, decides `TOOL_CALL` / `CLARIFICATION_NEEDED` / `BACKLOG_UNSUPPORTED` / etc. — never LLM-guessed |
| `registry.py` | The intent → `(subsystem, handler)` mapping — one entry per MVP intent |
| `clarification.py` | Fixed clarifying-question templates, keyed by which entity is missing |

### `app/tools/` — the actual handlers the router dispatches to
| File | Purpose |
|---|---|
| `live_data_tools.py` | LIVE_API handlers — thin wrappers around `FleetGPSClient`; live GPS data is always fetched, never persisted |
| `history_tools.py` | MONGO_REPO handlers — thin wrappers around the repository layer |
| `kb_tools.py` | RAG handlers — one per KB-backed intent (feature explanations, FAQ, troubleshooting, policy, pricing) |
| `general_knowledge.py` | The one KB-adjacent intent with no ingested source doc by design — answered directly by the LLM |
| `fleet_gps_client.py` | `FleetGPSClient` interface + `MockFleetGPSClient` — deterministic pseudo-random live data, seeded per vehicle so repeat calls are stable |

### `app/rag/` — retrieval-augmented generation pipeline (Phase 7)
| File | Purpose |
|---|---|
| `pipeline.py` | The orchestrator: retrieve → re-rank → assemble (gated for `pricing`) → generate, or fall back |
| `context_assembler.py` | Formats re-ranked chunks into a citable context block; also the pricing-leakage gate that excludes unapproved pricing content from non-PRICING queries |
| `reranker.py` | Self-hosted cross-encoder re-ranking (opt-in — measured to hurt precision when always-on) |
| `generation.py` | Cited generation — the LLM only phrases an answer from already-assembled context, never decides what's true |
| `fallback.py` | Fixed (non-LLM) fallback strings: no relevant KB content found, no approved pricing doc found |

### `app/kb/` — knowledge base ingestion & retrieval (Phases 4-5)
| File | Purpose |
|---|---|
| `chunker.py` | Structural chunking of `kb_sources/**/*.md` into `Chunk` objects |
| `embedder.py` | Self-hosted embedding model wrapper (`sentence-transformers/all-MiniLM-L6-v2`) — no external embedding API |
| `chroma_client.py` | ChromaDB client/collection accessors |
| `ingest.py` | Standalone CLI (`python -m app.kb.ingest`): chunk → embed → upsert into ChromaDB, sync `documents_meta` in Mongo. Idempotent — unchanged chunks are skipped by content hash. **Not** part of the request path; must be run manually/offline whenever `kb_sources/` changes or a fresh environment needs populating |
| `retrieve.py` | Minimal helper: embed a query, run top-k similarity search |

### `app/llm/` — swappable LLM provider (ADR 002)
| File | Purpose |
|---|---|
| `base.py` | The `LLMProvider` interface every provider implements |
| `factory.py` | `get_llm_provider()` — reads `LLM_PROVIDER` from config and builds the matching provider; never raises, falls back to `UnavailableLLMProvider` if misconfigured |
| `providers/openai_compatible.py` | Shared HTTP request/response logic for any OpenAI-compatible chat-completions API |
| `providers/deepseek.py` | DeepSeek adapter (paid, roadmap default) |
| `providers/groq.py` | Groq adapter (free-tier) — what this project actually runs against |
| `providers/unavailable.py` | Graceful-degradation fallback when no real provider is configured |
| `providers/fake.py` | Deterministic test double — used throughout the test suite, never at runtime |

### `app/memory/` — cross-turn conversation state (Phase 8)
| File | Purpose |
|---|---|
| `active_entity_tracker.py` | TTL-aware layer on top of `SessionRepository` tracking the last-referenced vehicle/driver/geofence per session, for pronoun resolution |
| `checkpointer.py` | LangGraph `MongoDBSaver` checkpointer wiring (ADR 005) — persists graph state per session/thread |

### `app/db/` — MongoDB access (Phase 3, ADR 001/004)
| File | Purpose |
|---|---|
| `client.py` | Motor (async) database connection |
| `schema_definitions.py` | `$jsonSchema` validators for every collection |
| `indexes.py` | Index definitions per collection |
| `init_db.py` | Idempotent setup — safe to re-run; existing collections get validators/indexes updated in place |
| `seed_data.py` | Synthetic demo data (fake company, vehicles, drivers, trips, etc. — nothing real) |
| `repositories/` | One repository per collection (`vehicle_repository.py`, `driver_repository.py`, `trip_repository.py`, `alert_repository.py`, `maintenance_repository.py`, `geofence_repository.py`, `session_repository.py`, `chat_message_repository.py`, `user_repository.py`) — **all** Mongo access goes through these, every method requires `company_id` (tenant scoping enforced at this layer, ADR 004) |

### `app/eval/` — AI evaluation harness (Phase 12)
| File | Purpose |
|---|---|
| `golden_set.py` | 44 hand-written Q&A cases covering every intent, with symbolic expected entities/citations |
| `scorer.py` | Pure scoring functions: intent accuracy, entity accuracy, retrieval precision, citation-groundedness |
| `runner.py` | Orchestrates running the golden set against real components (`python -m app.eval.runner [--real-llm]`) |

## MongoDB queries actually used

Every query in the app goes through `app/db/repositories/*.py` (ADR 001) — nothing outside that
folder talks to Motor directly except `app/kb/ingest.py` and `app/db/seed_data.py` (both
one-off/offline scripts, not request-path code) and `app/memory/checkpointer.py` (LangGraph's own
official checkpointer, which manages its own collections internally). Every query filters on
`company_id` except the one documented exception below (ADR 004).

### `vehicles` — `vehicle_repository.py`
| Method | Operation | Query |
|---|---|---|
| `find_by_plate_number` | `find_one` | `{company_id, plate_number}` |
| `find_by_nickname` | `find_one` | `{company_id, nickname: {$regex: "^<name>$", $options: "i"}}` |
| `get_by_id` | `find_one` | `{company_id, _id}` |
| `find_by_nickname_containing` | `find` (full scan, in-Python substring match) | `{company_id}` |
| `list_fleet_groups` | `distinct("fleet_group")` | `{company_id}` |
| `list_by_company` | `find` → `.sort("plate_number", 1).limit(n)` | `{company_id[, fleet_group]}` |
| `list_ids_by_fleet_group` | (composes `list_by_company`) | — |

### `drivers` — `driver_repository.py`
| Method | Operation | Query |
|---|---|---|
| `find_by_name` | `find` (case-insensitive exact match, returns a list to detect name collisions) | `{company_id, name: {$regex: "^<name>$", $options: "i"}}` |
| `get_by_id` | `find_one` | `{company_id, _id}` |
| `list_by_company` | `find` → `.sort("name", 1).limit(n)` | `{company_id}` |

### `trips` — `trip_repository.py`
| Method | Operation | Query |
|---|---|---|
| `find_trips` | `find` → `.sort("start_time", 1).limit(n)` | `{company_id, start_time: {$gte, $lt}[, vehicle_id][, driver_id]}` |
| `summarize_trips` | `aggregate`: `$match` → `$group` (`$sum` trip count + `$sum` distance) | match on `{company_id, start_time: {$gte,$lt}}` + `vehicle_id` or `vehicle_id: {$in: [...]}` |

### `alerts` — `alert_repository.py`
| Method | Operation | Query |
|---|---|---|
| `find_alerts` | `find` → `.sort("triggered_at", -1).limit(n)` | `{company_id, triggered_at: {$gte,$lt}[, vehicle_id][, driver_id][, alert_type]}` |
| `count_alerts_by_type` | `aggregate`: `$match` → `$group` by `alert_type` with `$sum: 1` | match on `{company_id, driver_id, triggered_at: {$gte,$lt}}` |

### `maintenance_records` — `maintenance_repository.py`
| Method | Operation | Query |
|---|---|---|
| `find_history` | `find` → `.sort("service_date", -1).limit(n)` | `{company_id, vehicle_id[, service_date: {$gte,$lt}]}` |
| `find_due` | `find` → `.sort("next_due_date", 1)` | `{company_id, next_due_date: {$lte: now + 14d}[, vehicle_id or vehicle_id: {$in:[...]}]}` |

### `geofences` — `geofence_repository.py`
| Method | Operation | Query |
|---|---|---|
| `find_by_name` | `find_one` | `{company_id, name: {$regex: "^<name>$", $options: "i"}}` |
| `list_for_vehicle_or_group` | `find` → `.sort("name", 1).limit(n)` | `{company_id, active: true[, $or: [{vehicle_ids}, {fleet_group}]]}` |

### `chat_sessions` — `session_repository.py`
| Method | Operation | Query |
|---|---|---|
| `create` | `insert_one` | new session doc |
| `get` | `find_one` | `{company_id, _id}` |
| `touch` | `update_one` `$set` | `{company_id, _id}` → sets `last_active_at` (drives the sliding-TTL index) |
| `get_active_entities` | (composes `get`) | — |
| `set_active_entity` | `update_one` `$set` | `{company_id, _id}` → sets `active_entities.<type>_id`, last-reference-wins (no history stack) |

### `chat_messages` — `chat_message_repository.py`
| Method | Operation | Query |
|---|---|---|
| `insert` | `insert_one` | new message doc |
| `list_for_session` | `find` → `.sort("created_at", 1).limit(n)` | `{company_id, session_id}` |

### `users` — `user_repository.py`
| Method | Operation | Query |
|---|---|---|
| `find_by_email` | `find_one` | `{email}` — **the one deliberate exception to the always-scope-by-`company_id` rule**: at login the caller's `company_id` isn't known yet, and `email` is globally unique (Phase 3's `users.email_unique` index), so this is safe and well-defined |
| `get_by_id` | `find_one` | `{company_id, _id}` |

### Offline/one-off scripts (not request-path code)
| File | What it queries |
|---|---|
| `app/kb/ingest.py` | `documents_meta.update_one(..., upsert=True)` — keeps Mongo's doc registry in sync with what was just chunked/embedded into ChromaDB |
| `app/db/seed_data.py` | `insert`/`update_one(..., upsert=True)` across `users`, `vehicles`, `drivers`, `trips`, `alerts`, `maintenance_records`, `geofences`, `chat_messages`, `documents_meta` — synthetic demo data only |
| `app/eval/runner.py` | `vehicles.insert_one` / `drivers.insert_one` — seeds fixtures the golden-set cases resolve entity expectations against |

### Not hand-written queries: LangGraph's own collections
`app/memory/checkpointer.py` wires up the official `MongoDBSaver`, which manages
`langgraph_checkpoints` and `langgraph_checkpoint_writes` internally — this codebase never
queries those collections directly, only through the saver's `aget_tuple`/`aput`/`alist` methods.

### Patterns worth noting
- **Every list-returning query has `.sort()` + `.limit()`** — no unbounded scans in the request
  path except `vehicle_repository.find_by_nickname_containing`, explicitly documented as an
  acceptable full scan at pilot scale (small fleets per company, <50 concurrent users).
  - **Case-insensitive name/nickname matches use `$regex: "^...$"` with `$options: "i"`**, anchored
  and `re.escape`d — never a raw string interpolated into the pattern.
- **Aggregation is used only for real grouping/summing** (`summarize_trips`,
  `count_alerts_by_type`) — everything else is a plain `find`/`find_one`, kept as simple as the
  question actually requires.
- **`company_id` is a required, non-defaulted parameter on every method except
  `find_by_email`** — tenant scoping is enforced at this layer (ADR 004), not left to callers to
  remember.
